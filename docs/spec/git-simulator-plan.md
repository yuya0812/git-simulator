## 技術方針

### 全体構成

画面（React）と Git の動き（シミュレーションエンジン）を完全に分ける。

```text
src/
├── engine/        Git の動きを再現する純粋な TypeScript（React に依存しない）
│   ├── types.ts       State / Commit / PullRequest などの型
│   ├── initial.ts     初期状態と自己紹介ページの3ファイル
│   ├── graph.ts       祖先判定・共通祖先（merge base）・変更ファイル判定
│   ├── operations/    clone / branch / switch / edit / restore / stage / commit /
│   │                  push / pull / pr / approve / merge / deleteBranch / teammate
│   └── result.ts      操作結果（成功 / 拒否 / 警告付き）とイベント
├── hints/         イベント → 「今起きたこと」「次にできること」の文章
├── command/       コマンド入力 → エンジン操作への変換
├── store/         Zustand ストア（エンジンを呼び、結果を画面に渡す）
├── components/    画面部品
│   ├── files/         ファイル一覧・エディタ・restore ボタン
│   ├── graph/         LOCAL / REMOTE のグラフ（SVG）
│   ├── staging/       ステージング欄
│   ├── preview/       iframe プレビュー（3モード）
│   ├── diff/          Diff 表示
│   ├── hint/          ヒント欄
│   └── controls/      操作ボタン・コマンド入力・ダイアログ
└── App.tsx
```

**理由:** 要件の中心は「Git の状態がどう変わるか」であり、ここが正しくないと教材として成立しない。エンジンを React から切り離して単体テストで固めることで、画面を作り込む前に Git の挙動を保証できる。

### エンジンの操作の形

すべての操作を同じ形の純粋関数にする。

```ts
type OpResult =
  | { kind: "ok"; state: State; event: SimEvent }               // 成功
  | { kind: "needsConfirm"; warning: Warning; proceed: () => OpResult } // main への直接操作・ローカル merge
  | { kind: "rejected"; reason: Rejection };                     // 切り替え不可・push 拒否・Conflict など
```

- `event` は「何をした / 何が変わった / 何は変わっていない」を作る材料（ヒント欄が使う）
- `rejected` はエラーではなく説明を出すための情報（要件 9章・10.2）
- ボタンもコマンド入力も、最終的に同じ操作関数を呼ぶ

### データモデル（要件 15章の詳細化）

```ts
type FileName = "index.html" | "style.css" | "script.js";
type Files = Record<FileName, string>;

type Commit = {
  id: string;              // "A", "B", "C"...
  message: string;
  parents: string[];       // マージコミットは2つ
  author: "you" | "teammate";
  files: Files;            // 全ファイルのスナップショット（最重要）
};

type State = {
  commits: Record<string, Commit>;   // 全コミット（LOCAL / REMOTE 共通の置き場）
  nextIdIndex: number;
  remote: { branches: Record<string, string> };
  local: null | {                    // clone 前は null
    branches: Record<string, string>;
    current: string;                 // 今いるブランチ
    index: Files;                    // ステージング（次のコミットになる全体の状態）
    workingTree: Files;              // 編集中のファイル
  };
  pullRequests: PullRequest[];       // from / to / status: open | approved | merged
  phase: "beforeClone" | "beforeBranch" | "free";  // 序盤の固定手順（要件 7.2）
};
```

- **ステージングは「全体のスナップショット」として持つ**（本物の Git の index と同じ）。stage は「そのファイルを workingTree から index へコピー」、commit は「index をそのまま新しいコミットにする」。これで要件 10.1 の「1つだけステージングしてコミットすると、もう1つは古いまま記録される」が自然に再現できる
- **コミットの置き場は1つ**。LOCAL / REMOTE それぞれのグラフには「そちら側のブランチからたどれるコミット」だけを表示する。push / pull は「相手側のブランチ名札を動かす」ことに相当する
- コミット ID はチームメイトのコミットとマージコミットも含め、作られた順に A, B, C... と振る

### 主な判定ロジック（graph.ts）

| 判定 | 方法 | 使う場面 |
|---|---|---|
| 祖先判定 | 親をたどって到達できるか | push 拒否、pull の fast-forward 判定、「すでに取り込み済み」判定 |
| 共通祖先（merge base） | 両方の祖先集合の共通部分のうち最も新しいもの | Conflict 判定、変更ファイル判定 |
| 変更ファイル | 2つのスナップショットをファイル単位で比較 | Conflict 判定、チームメイトのファイル選択 |
| Conflict | merge base から見て、両側で変更されたファイルが重なるか | merge / pull の停止（要件 9章） |
| ユーザーが変更したファイル | 編集中・ステージング中のファイル ＋ 各ローカルブランチで「リモート main との merge base から変更したファイル」 | チームメイトのファイル選択（要件 8章、21.1） |

### プレビュー

- iframe の `srcdoc` に、index.html へ style.css / script.js を埋め込んだ HTML を渡す
- `sandbox="allow-scripts"` のみ付与し、親ページへのアクセスはさせない
- 表示モード: 手元の編集中（workingTree）/ GitHub の main / 選択したコミット

### 使用ライブラリ

技術スタックの判断基準にもとづき、追加するパッケージは最小限にする。**以下はインストール前に承認をもらう。**

| 用途 | パッケージ | 理由 |
|---|---|---|
| 土台 | react / react-dom / typescript / vite | 要件で確定済み |
| スタイル | tailwindcss | 要件で確定済み |
| 状態管理 | zustand | 技術スタック方針（シンプルな場合は Zustand） |
| テスト | vitest | エンジンの単体テスト。Vite と設定を共有できる |
| Diff | diff（jsdiff） | 行単位の差分計算。自作すると時間がかかるうえにバグが出やすい |

使わないもの:

- **グラフ描画ライブラリ**: コミット数は多くても十数個なので、SVG を自前で描く。LOCAL / REMOTE を左右に並べる独自の見せ方にも合わせやすい
- **コードエディタ（CodeMirror など）**: 最初は textarea で作る。3ファイル・数十行で、未経験者向けには十分。必要になったら後から入れ替える
- **アニメーションライブラリ**: CSS / SVG のトランジションで足りる見込み

### 公開

- GitHub Pages に GitHub Actions でデプロイする（main への push でビルド・公開）
- Vite の `base` をリポジトリ名に合わせる

## リスク・懸念点

| リスク | 対策 |
|---|---|
| MVP がすべての機能を含むため規模が大きい | エンジン（Phase 1〜2）を先に固め、画面は Phase ごとに動く状態を保つ。途中で区切って公開できるよう、Phase 4 終了時点で一周が操作できることを目標にする |
| グラフの配置が複雑になる（マージ、チームメイトのコミット、ブランチ削除） | コミット数が少ない前提で単純なレーン割り当てにする。Phase 5 の最初に配置ルールを決めてから描く |
| 「ユーザーが変更したファイル」の判定が漏れて Conflict が起きる | 判定を graph.ts に集約し、チームメイト → merge / pull のシナリオテストで保証する。それでも重なった場合は Conflict 停止の説明が出るので、画面が壊れることはない |
| ユーザーが書いた JS がプレビューで動く | iframe を sandbox（allow-scripts のみ、同一オリジン不可）にして、親ページや他のデータには触れさせない。サーバーも保存もないので外部への影響はない |
| ヒント文言の量が多く、品質がばらつく | 文言を hints/ に集約し、Phase 3-4 と 8-3 で通して見直す |
| PR 承認のタイマーが操作と競合する | エンジンは「承認する」操作だけを持ち、タイマーはストア側に置く。承認前に PR が merge されることはない仕組みにする |
