# Git Simulator

**コマンドを覚える前に、Git の世界を動かしてみよう。**

Git 完全未経験者が、ボタン操作で clone から pull までを一周しながら、「Git の中で今何が起きているのか」を目で見て理解するための学習用 Web アプリです。

## AI 駆動開発で作っています

このアプリは、要件定義から実装・検証まで、AI と壁打ちしながら作っています。AI に任せきりにするのではなく、**AI が案や指摘を出し、人間が判断して決める**ことを徹底しました。

```text
アイデア
  ↓ ChatGPT に一発で書かせる
要件定義書 v1.0  ……… 勢いはあるが、矛盾や抜けが残っている
  ↓ Claude Code がレビューして問題点を指摘
  ↓ 1問ずつヒアリングし、人間が全項目を決める
要件定義書 v1.1  ……… 主な変更点は15項目。変更箇所にはラベルを付けて差分を残した
  ↓ Claude Code が実装計画を作り、人間が承認
実装計画
  ↓ フェーズごとに「実装 → テスト → 実画面で確認 → 人間がレビュー」
アプリ
```

### 役割分担

| 担当 | やったこと |
|---|---|
| 人間（私） | アイデア出し、ヒアリングでの意思決定、各フェーズの承認、触ってみての改善指示 |
| ChatGPT | アイデアから要件定義書 v1.0 のたたき台を生成 |
| Claude Code | v1.0 のレビュー、ヒアリングの進行、要件定義書 v1.1 と実装計画の作成、実装、テスト、ヘッドレスブラウザでの動作確認 |

### 壁打ちで変わったこと

ChatGPT 版の [要件定義書 v1.0](要件定義書_v1.0.md) と、壁打ち後の [要件定義書 v1.1](要件定義書.md) を、どちらもリポジトリに残しています。v1.1 の冒頭に変更点の一覧があります。たとえば次のような問題を、Claude Code のレビューで見つけて直しました。

| v1.0 の問題 | 壁打ちで決めたこと |
|---|---|
| PR を merge したところで終わるので、「GitHub で merge したのに手元の main が古いまま」を教えられない | ゴールを pull まで広げ、clone から一周する流れにした |
| merge のシナリオで開発ラインが分かれておらず、「別々に進んだラインを統合する」という説明と合わない | PR の merge は常にマージコミットを作る。チームメイトを登場させ、本当に分かれたラインを作れるようにした |
| ブランチを作った直後の図が、別の線が伸びているように見える | 「同じコミットに名札が2枚付いている」状態として見せる |
| ステージングがない | 「選んでコミット」まで扱う |
| ターゲットが「未経験〜使用歴1年」と広く、説明の深さが決まらない | Git 完全未経験者に絞る |

ヒアリングは6テーマ・40問以上を1問ずつ行い、そのあと未確定の8項目も追加で確定させました（[ヒアリングメモ](ヒアリングメモ.md)）。

### 実装中も、人間が触って判断する

フェーズの区切りごとに実際の画面を確認し、気になったところを AI に伝えて直しています。

- 「1画面に詰め込みすぎて窮屈」→ 縦スクロールにして、操作ボタンだけ画面下に固定した。ヒント欄が画面の外に出ても結果を見逃さないよう、固定バーに直前の結果を1行で出す案を AI が追加で提案した
- 「ボタン操作だけだと、本物の Git の CLI と結びつかない」→ 各操作に対応する `git` コマンドを表示した
- 「ブランチを作ったら自動で移動する？」という AI からの確認に対して → 自動では移動せず、「移動しますか？」と聞く形にした

### AI に任せるときのルール

- コミットやファイルの削除などの取り返しにくい操作は、毎回人間の承認を得てから実行する
- 要件にない仕様を AI が決めたときは、決めた内容と理由を報告させ、要件定義書や計画書に書き残す
- 「テストが通った」だけで終わらせず、ヘッドレスブラウザで実際にボタンを押して画面を確認する

## なぜ作ったか

Git の入門で、多くの人が次のようにつまずきます。

```text
commit = 変更したファイルを保存するもの？
branch = ファイルを分けるフォルダ？
push   = GitHub 全体に変更を反映する？
```

原因はコマンドを知らないことではなく、次の3つを区別できていないことだと考えました。

1. **「プロジェクト全体の状態」と「変更差分」**: コミットは差分ではなく、その時点のプロジェクト全体の記録
2. **「ブランチ」と「フォルダ・コピー」**: ブランチはコミットに付いた名札
3. **「自分の PC の Git」と「GitHub の Git」**: 両者は別々に存在し、push / pull するまでずれている

このアプリは、コマンドの暗記ではなく、この3つの区別を体験で身につけることを目的にしています。

## 特徴

### 操作するたびに「何が変わらなかったか」まで説明する

操作のたびに、ヒント欄に次の3つを表示します。

- **何をした？**
- **何が変わった？**
- **何は変わっていない？**

初心者がつまずくのは「変わったもの」より「変わっていないもの」です。たとえば、GitHub で PR を merge しても、自分の PC の main は古いままです。

```text
何をした？           PR #1 を merge しました
何が変わった？       GitHub の main の名札が、2つのラインを合わせた コミット C に移動した
何は変わっていない？ 自分のPCの main（まだ古いままです）
```

### 自分の PC と GitHub を、別々の箱として並べる

LOCAL（自分の PC）と REMOTE（GitHub）を左右に並べて表示します。push / pull のたびに両方のブランチの位置を見比べられるので、両者がずれていく様子と、それが揃う瞬間が目に見えます。

### ボタン操作と、本物の Git のコマンドを結びつける

操作はボタンが中心ですが、ダイアログと操作後のヒント欄に「本物の Git だと」として、対応するコマンドを表示します。

```text
本物の Git だと
$ git push -u origin feature/profile
-u は「このブランチは GitHub の同じ名前のブランチとつながっている」と覚えさせる指定です。
```

### 間違った操作をエラーにしない

コミットしていない変更があるときのブランチ移動や、GitHub の方が先に進んでいるときの push は、実行せずに理由を説明します。

```text
ちょっと待って: GitHub にあなたの知らない変更があります
このまま送ると、その変更を上書きして消してしまうので、Git は送るのを止めます。
先に pull して、その変更を取り込んでから push しましょう。
```

main への直接 push のような「Git としては正しいが、チーム開発では避ける操作」は、確認を挟んだうえで実行できます。

### チームメイトを登場させられる

「チームメイトが main を更新」ボタンで、GitHub だけが先に進んだ状態を作れます。push が拒否される → pull する → push が通る、という実務でよくある流れを体験できます。

## 体験できること

| 操作 | 内容 |
|---|---|
| clone | GitHub のプロジェクトを履歴ごと自分の PC にコピー |
| ブランチ作成 / 移動 | 作った直後は main と同じコミットを指すこと、移動しても中身が変わらないことを確認 |
| 編集 / ステージング / コミット | 2つ変更して1つだけステージングすると、もう1つは古い状態のまま記録される |
| push / pull | 自分の PC と GitHub のずれと、その解消 |
| PR / 承認 / merge | チームメイトの承認を経て、GitHub 上で取り込む |
| ローカル merge | 自分の PC で直接取り込む（警告付き） |

仮想プロジェクトは `index.html` / `style.css` / `script.js` の3ファイルだけの自己紹介ページです。

## 設計

### 全体構成

画面（React）と Git の振る舞い（エンジン）を完全に分けています。

```text
src/
├── engine/      Git の振る舞いを再現する純粋な TypeScript（React に依存しない）
│   ├── types.ts       State / Commit / PullRequest などの型
│   ├── graph.ts       祖先判定・共通祖先・Conflict 判定・スナップショットの合成
│   └── operations/    clone / branch / commit / push / pull / PR / merge ...
├── hints/       操作結果 → 「今起きたこと」「次にできること」「本物の Git のコマンド」
├── store/       Zustand ストア（エンジンを呼び、結果を画面に渡す）
└── components/  画面部品
```

教材として一番大事なのは「Git の状態が正しく変わること」です。エンジンを React から切り離して単体テストで固めてから、画面を作っています。

### 主な設計判断

**すべての操作を、同じ形の純粋関数にする**

```ts
type OpResult =
  | { kind: 'ok'; state: State; event: SimEvent }   // 成功。event がヒント欄の文章の材料になる
  | { kind: 'rejected'; rejection: Rejection }      // 実行しない。理由を説明するための情報
  | { kind: 'needsConfirm'; warning: Warning }      // 確認を挟む。confirmed: true で再実行
```

「拒否」をエラーではなくデータとして返すことで、間違った操作をしたときにも、理由を説明する文章を作れます。

**コミットに、プロジェクト全体のスナップショットを持たせる**

各コミットは差分ではなく、3ファイルすべての中身を持っています。ステージング（index）も同じく「全体のスナップショット」として持つので、本物の Git と同じ次の挙動が自然に再現されます。

> 2つのファイルを変更して1つだけステージングしてコミットすると、もう1つは変更前の状態で記録される。

**Conflict を起こさない**

完全未経験者向けのため、Conflict の解決は扱いません。両側で同じファイルを変更している merge / pull は実行せずに説明します。チームメイトは「ユーザーがまだ変更していないファイル」だけを変更します。どちらも、共通祖先からの変更ファイルを比べる同じ仕組みで判定しています。
